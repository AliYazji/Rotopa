# قائمة التحقق قبل الإطلاق

حالة حقيقية اعتباراً من هذا التاريخ (2026-09-16) — **DONE** = مبني ومختبر ومُتحقَّق منه حياً،
**جزئي** = جزء حقيقي منه فقط، **غير مبني** = لم يُلمس بعد، **مؤجَّل بقرار** = تُرك عمداً وموثَّق لماذا.
لا شيء هون مبالغ فيه أو مخمَّن — كل سطر يعكس ما حصل فعلياً هالجلسة أو قبلها.

## 1. إدارة المستخدمين والأدوار والصلاحيات — DONE
دعوة عضو (بريد جديد → دعوة معلَّقة تُفعَّل تلقائياً، بريد له حساب → عضوية فورية)، تعديل دور/فرع/تفعيل،
حماية الأدوار النظامية الثلاثة، منع تعطيل آخر مالك مُفعَّل. `20250911002900_team_management.sql`،
صفحتا `/team` و`/roles`.

## 2. إدارة الفترات المحاسبية (إقفال/فتح) — DONE
إقفال بترتيب زمني إلزامي، فتح بترتيب عكسي إلزامي وبسبب إلزامي، السنة كقفل رئيسي، سجل دائم لكل عملية.
`20250911003000_period_closing.sql`، صفحة `/periods`.

## 3. سجل التدقيق — DONE
استعلام مفلتر (جدول/عملية/مستخدم/معرّف سجل/تاريخ) مع ترقيم صفحات، عرض فرق قبل/بعد. `/audit-log`.

## 4. الأمان وتهيئة بيئة الإنتاج — **جزئي**
- CI/CD (فحص تلقائي عند كل push): **DONE** — `.github/workflows/ci.yml` (اختبارات SQL + بناء الويب +
  فحص أنواع ETL + اختبار تزامن) و`backup-verify.yml` (تحقّق أسبوعي من الاستعادة). **لم يُشغَّل فعلياً
  على GitHub بعد** — محاكى محلياً بدقة فقط، لا push حصل لهالفرع.
- النسخ الاحتياطي والاستعادة: **DONE** — `scripts/backup-db.sh`/`restore-db.sh`، مُتحقَّق منهما حياً
  بدورة نسخ→استعادة→تشغيل الاختبارات الكاملة على النسخة المُستعادة.
- بيئات منفصلة (تطوير/تجريب/إنتاج): **غير مبني** — لا يوجد إلا بيئة تطوير محلية واحدة حتى الآن.
  المشروع لم يُربَط بـ Supabase Cloud بعد (`npx supabase link` لم يُشغَّل).
- HTTPS/CORS: **غير مبني بالكود — مسؤولية النشر**. Supabase Cloud يفرض HTTPS تلقائياً؛ CORS يُضبط من
  لوحة Supabase (Authentication → URL Configuration) وقت الربط الفعلي بنطاق Cloudflare Pages —
  خطوة تُنفَّذ عند النشر الحقيقي، موثَّقة بـ `docs/deployment.md`، لم تُنفَّذ فعلياً لعدم وجود نطاق بعد.
- تحديد المعدل (Rate limiting): **غير مبني**. Supabase Cloud يوفّر حداً افتراضياً على مستوى المنصة؛ لا
  تحديد إضافي خاص بهذا التطبيق (لا حاجة له بمستخدمين معدودين لمؤسسة واحدة — إعادة تقييم لو صار
  استخدام متعدد المؤسسات لاحقاً).
- **بند أمان حقيقي يجب حسمه قبل الإطلاق**: شاشة تسجيل الدخول (`Login.tsx`) تسمح بـ`supabase.auth.signUp`
  مفتوح لأي بريد — أي شخص يقدر يسجّل حساباً جديداً ويصل لشاشة "إنشاء مؤسسة". لمؤسسة واحدة (كحال
  RETAJ الحالية) **يجب تعطيل التسجيل العام** من لوحة Supabase (Authentication → Providers → Email →
  إيقاف "Allow new users to sign up") بعد إنشاء حسابات الفريق المطلوبة، والاعتماد فقط على آلية
  الدعوة المبنية بالبند 1. لم يُعطَّل بعد — لسا محلي.

  التدقيق، لا أداة APM مخصّصة لأنه لا خادم backend خاص).
- دليل مستخدم (End-user manual): **غير مبني**.
- دليل مدير النظام (Sysadmin guide): **غير مبني** — أقرب ما موجود هو `docs/deployment.md` نفسه، لكنه
  للنشر التقني لا للاستخدام الإداري اليومي.
- مصفوفة الصلاحيات (Permission matrix — أي دور يقدر يعمل شو، بجدول واحد): **غير مبنية** — الصلاحيات

  مستند واحد يلخّصها كجدول مرجعي جاهز للطباعة/المشاركة مع فريق غير تقني.

## 6. الاختبارات الحقيقية (E2E + أداء + تزامن) — DONE، بقيد واحد صريح
- سيناريو أعمال متكامل عابر للوحدات (فريق→دليل حسابات→مورد وعميل→شراء→بيع جزئي→دفعة→مرتجع→إقفال
  فترة): `supabase/tests/270_workflow_e2e.sql`.
- اختبار تزامن حقيقي (عمليتان متوازيتان فعلياً، لا محاكاة): `supabase/tests/concurrency/run.sh` —
  مُدمج بـ`ci.yml` ليعمل تلقائياً.
- فحص أداء أساسي (300 قيد محاسبي، تنبيه انحدار لا معيار قياس حقيقي — لا بيانات إنتاج فعلية للمقارنة
  عليها بعد): `supabase/tests/performance/bulk-posting.sql`.
- **القيد الصريح**: لا توجد أداة تشغيل متصفح بهالبيئة طوال الجلسة — **كل تحقّق كان على مستوى
  الـ API/قاعدة البيانات المباشر، لا نقر فعلي على الواجهة بالعين**. كل ميزة هالجلسة (الفريق، الأدوار،
  الفترات، سجل التدقيق، اللوحة الرئيسية) تحتاج مراجعة بصرية حقيقية بمتصفح فعلي قبل الاعتماد الكامل
  عليها بالإنتاج.

## 7. نضج الواجهة التجارية — **جزئي**
- لوحة تحكم KPI حقيقية: **DONE** — `/` (نقد/ذمم/مبيعات ومشتريات الشهر/حالة الفترة/قائمة انتظار/آخر
  النشاطات).
- إشعارات: **مبسَّطة عمداً، ليست نظاماً حقيقياً** — مؤشر واحد (badge بعدد "بانتظار الإجراء") بأعلى
  الشريط الجانبي، معاد استخدام لأرقام اللوحة الرئيسية، بلا تخزين أو تنبيه لحظي (realtime) أو إمكانية
  رفض/تأجيل إشعار فردي. نظام إشعارات حقيقي (جدول + realtime + حالة مقروء/غير مقروء) قرار مستقبلي
  منفصل لو احتاج المستخدم أكثر من هيك.
- قوالب طباعة: **جزئي** — فاتورة المبيعات فقط (`components/PrintInvoice.tsx`، مطبَّق بـ
  `SalesInvoiceDetail.tsx`). فواتير المشتريات والمرتجعات والسندات **ما إلها طباعة بعد** — نفس
  المكوّن قابل لإعادة الاستخدام مباشرة لأي منها، لم يُوصَل فقط.
- إعدادات متقدمة: **DONE** (تحديث لاحق لهذا البند — كان "جزئي" وقت كتابته). صفحة `/settings` صارت
  فيها: اسم المؤسسة، بيانات الطباعة، **نسبة ضريبة قابلة للتعديل والتعطيل لكل مؤسسة** (`org_settings`
  `key='tax'`، `20250911003500_configurable_tax.sql`)، **حسابات افتراضية** (مبيعات/ضريبة مخرجات/
  ضريبة مدخلات/صندوق) تُعبّى تلقائياً بكل نموذج ترحيل، و**صناديق كاشير محدَّدة** بدل القائمة الكاملة.
  دليل حسابات افتراضي حقيقي (285 حساب) صار يُزرع تلقائياً لأي مؤسسة جديدة (`20250911003800_default_coa.sql`).
  ورديات صندوق (جرد/إقفال/عجز/زيادة) مبنية أيضاً (`20250911003900_cash_shifts.sql`).
